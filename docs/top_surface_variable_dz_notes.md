# 顶部可变 dz 方案讨论总结（telefd2d）

日期：2026-02-18

## 1. 当前实现现状（为什么“直接改一层 dz(x)”不合法）

当前求解器是规则笛卡尔网格，`dz` 作为全局常数参与所有 z 向差分与 z 向 CPML。

- 网格定义中 `dz_m` 是标量：`src/fd_workflow/config.py:38`
- 地形通过 `surface_idx` 做台阶化（PM 分类），不是变形网格：`src/fd_workflow/model.py:49`
- Python 核心里 z 向导数统一使用 `/dz`：`src/fd_workflow/solver.py:158` `src/fd_workflow/solver.py:172` `src/fd_workflow/solver.py:204`
- C++ 核心同样统一使用 `/dz`：`src/fd_workflow/_fd_core.cpp:328` `src/fd_workflow/_fd_core.cpp:348` `src/fd_workflow/_fd_core.cpp:393`

结论：只把最上层几何解释为 `dz(x)`，但方程仍按常数 `dz` 离散，会造成离散算子与几何不一致，因此不合法。

## 2. 对差分格式的影响

有实质影响，且不是局部“改一条公式”就能闭合。

- 常系数中心差分会变成位置相关系数的非均匀差分（至少涉及所有跨顶部可变层的 `∂/∂z` 项）。
- 自由表面离散闭合条件需与新几何一致，否则容易引入伪反射。
- z 向 CPML 若仍按统一 `dz` 构建，需确认与顶部局部变 `dz` 的区域隔离或保持一致推导。

## 3. 工程改造量评估

中到大。

- 仅 Python 原型（验证思路）：约 2-4 天。
- Python + C++ 双后端一致 + 回归验证：常见为 1-2 周量级。

此外，本仓库当前 run 目标写明固定 `dx=dz=20m`：`AGENTS.md:4`。若引入顶部 `dz(x)`，属于超出当前既定约束的功能改造。

## 4. 是否可以“仅在顶部改变差分格式”

可以，但必须是“顶部邻域成套改造”，不能只改一个网格层的一条更新式。

- 可行做法：内部保持原格式，仅在自由表面附近 1-2 层（按交错网格实际耦合范围）使用局部 z 向差分系数。
- 必要条件：所有会跨越该可变层的应力/速度更新项都要同步改；自由表面条件也要用同一套几何假设。
- 风险点：如果只改 `j=0` 或只改某个方程，会出现相位误差、假反射或局部不稳定。

## 5. 极小 dz 的问题（为什么要设下限）

若顶部某些位置 `dz_min` 过小，会触发典型小单元问题：

- CFL 约束被 `dz_min` 主导，`dt` 必须显著减小，否则近地表先发散。
- 即便稳定，计算步数会显著增加，运行时长上升明显。
- 局部系数变硬（`1/dz` 变大），更易出现高频噪声与伪反射。

工程上通常给顶部厚度加下限，例如：

- `dz_top(x) >= 0.3~0.5 * dz_background`
- 低于下限时做厚度合并或平滑，避免极薄单元。

## 6. 建议落地顺序

1. 先做 Python 原型，只改近表层离散，验证稳定性与误差。
2. 通过后再迁移到 C++ 核，保持两后端结果一致。
3. 最后做参数约束（`dz_min`、平滑、CFL 自动收紧）和回归基线更新。
